# ممیزی فنی پروژه — ۲۰۲۶-۱۱-۰۳

دامنه: بررسی کد همین شاخه؛ امتیازهای آمادگی در `PRODUCT_READINESS_SCORECARD.md` ارزیابی تجربی یا تضمین امنیت نیستند. وضعیت اجرا و دستگاه واقعی جداگانه باید سنجیده شود.

## معماری موجود

- اپ اندروید Kotlin/Compose؛ `AppContainer` وابستگی‌ها را lazy می‌سازد؛ Room برای مکالمه/فضای کاری، SharedPreferences+AndroidKeyStore برای کلیدها، OkHttp/Moshi برای API.
- `ZipWorkspaceManager` آرشیوها را در حافظهٔ خصوصی نگه می‌دارد، `WorkspaceDiffEngine` تغییر فایل‌ها را با SHA-256 تعیین می‌کند، `WorkspaceMergeEngine` نسخهٔ مشتق‌شده می‌سازد. مراحل شش‌گانهٔ Project Lab پرامپت هستند، نه اجرای خودکار تست یا ادغام معنایی.
- زمینهٔ ارسالی به مدل مجموعه‌ای محدود از قطعات فایل است، نه کل پروژه. برچسب «مشاهده‌شده» در پاسخ AI تضمین درستی نیست.

## یافته‌ها و اقدام انجام‌شده

| اولویت | شاهد و اثر | اصلاح همین مرحله |
|---|---|---|
| P0 | `ZipWorkspaceManager.extractZipToWorkspace`: `ZipInputStream` روی بایت تصادفی `nextEntry == null` می‌داد و می‌توانست پروژهٔ خالیِ ظاهراً موفق بسازد؛ آرشیو بدون دایرکتوری مرکزی هم ممکن بود به‌صورت ناقص پذیرفته شود. | اعتبارسنجی دایرکتوری مرکزی با `ZipFile`، رد ZIP خالی، تست فایل نامعتبر/بریده‌شده و پاکسازی پس از خطا. |
| P0 | محاسبهٔ حجم موجود پیش از `try`، پس از ساخت پوشه انجام می‌شد؛ خطای IO می‌توانست پوشهٔ یتیم بگذارد. لغو coroutine در حلقه‌های IO به‌موقع دیده نمی‌شد. | انتقال preflight به `try` و کنترل لغو در کپی و استخراج؛ پاکسازی سپس انتشار `CancellationException`. |

| P1 | `getRelevantWorkspaceChunks`: فایل‌های نامرتبط قبل از فایلِ مرتبط خوانده می‌شدند، یک فایل می‌توانست همهٔ قطعات همان نسخه را مصرف کند. | رتبه‌بندی مسیر قبل از رمزگشایی متن، سقف ۱۲۸ فایل خوانده‌شده، ۱۶ واژهٔ پرس‌وجو و ۲ قطعه از هر فایل؛ حذف متنِ NULدار و افشای این محدودیت در متن تحلیل. |

| P1 | فهرست فایل‌های محرمانه/الگوی AWS access key در `RemoteContextGuard` کامل نبود. | اضافه‌شدن `.npmrc`، `.netrc`، `secrets.yaml` و کلید دسترسی رایج؛ تست رگرسیون. این فیلتر همچنان best-effort است. |

## ریسک‌های باز، به ترتیب اولویت

1. **P0 — شفافیت/کنترل ارسال داده:** پنجرهٔ رضایت در `ChatScreen.kt` فقط تعداد فایل‌ها را می‌گوید؛ پیش‌نمایش دقیق متن نهایی و ارائه‌دهندهٔ حالت Auto پیش از ارسال وجود ندارد. کاربر باید بتواند *دقیقاً* متن حذف‌شده/ارسالی و هزینهٔ تخمینی را تأیید کند. Regex هرگز جای طبقه‌بندی داده و انتخاب صریح فایل‌ها را نمی‌گیرد.
2. **P0 — سازگاری داده پس از کرش:** کپی نسخهٔ مشتق‌شده مستقیماً به `sali_workspaces/<id>` انجام می‌شود و سپس Room نوشته می‌شود (`ZipWorkspaceManager`/`WorkspaceRepository`). کرش میان این دو می‌تواند پوشهٔ یتیم بسازد؛ حذف هم ابتدا فایل و سپس رکورد را پاک می‌کند. نیازمند پوشهٔ staging، بازیابی startup در IO، و تست قطع برق/کرش است.
3. **P1 — پوشش و استناد:** manifest پایدار SHA-256 به ازای همهٔ فایل‌ها، diff خط‌به‌خط، درصد فایل‌های بازرسی‌شده و ارجاع قابل‌کلیک نسخه/مسیر/خط نداریم. `WorkspaceDiffEngine` هنگام هر مقایسه دوباره فایل‌ها را هش می‌کند و `ignoredFileCount` را گزارش نمی‌کند.
4. **P1 — کیفیت انتشار:** `build-apk.yml` تست/ساخت/امضا را کنترل می‌کند اما lint به‌خاطر خطای AGP/KSP غیرمسدودکننده است؛ امضای ثابت، پوشش تست و ماتریس دستگاه‌های API 24/RTL/TalkBack اثبات نشده‌اند.
5. **P1 — کارایی واقعی:** `analyzeWorkspace` و مقایسهٔ هش کل فایل‌ها را تکرار می‌کنند؛ زمان شروع سرد، dropped frames، مصرف RAM و باتری روی سخت‌افزار ضعیف هنوز benchmark نشده‌اند. کاهش نظری کار کافی نیست.
6. **P2 — محصول تجاری:** سیاست‌ها وجود دارند، اما انتخاب LICENSE، پرداخت، پشتیبانی، کنترل حذف/صادرات کامل، فهرست فروشگاهی و تأیید حقوقی مستقل در این مخزن اثبات نشده‌اند.

## معیار خروج برای نسخهٔ فروش‌پذیر

- صفر مورد باز P0، lint مسدودکننده و سبز، انتشار فقط با امضای ثابت، تست نصب روی نسخهٔ قبلی؛ هیچ APK با کلید موقت به عنوان نسخهٔ تولید عرضه نشود.
- اندازه‌گیری cold start p50/p95، jank و زمان تحلیل ZIP روی حداقل یک گوشی کم‌قدرت API 24 و یک گوشی جدید؛ هدف‌ها باید **پس از baseline واقعی** تعیین شوند.
- هر گزارش تحلیل: تعداد فایل‌های واجد شرایط/خوانده‌شده/حذف‌شده، دلیل حذف، مدل/ارائه‌دهنده، و وضعیت واقعی اجرای تست و build؛ «ندیده» هرگز «وجود ندارد» تلقی نشود.
- تست ضدبدافزار ZIP، لغو و بازیابی، فایل دودویی با پسوند کد، و تعارض فایل/پوشه در merge؛ تأیید دستی RTL، دسترس‌پذیری و جریان کامل کاربر.
